# v1.7 从故障时段关联到具体请求

在已有 HTTP 历史调查目标中配置 `health.service_log_path`、`prometheus` 和 `jaeger`。日志使用 JSONL，每行提供 `timestamp`、`service`、`level`，可附带 `trace_id`。服务名与 `prometheus.service` 精确匹配。Jaeger 连接方式沿用 v1.6，配置值为 `jaeger.base_url`，按需使用 `OPSPILOT_JAEGER_TOKEN` 提供只读令牌。 [历史调查配置](v1.2-incident-window.md) · [Jaeger 配置](v1.6-request-trace.md)

```jsonl
{"timestamp":"2026-11-27T08:20:55Z","service":"gateway","level":"ERROR","trace_id":"037d2e50c4e749c18120de699d0e7d8f"}
```

```powershell
$range = @('--config', 'target.json', '--incident-start', '2026-11-27T08:19:25Z', '--incident-end', '2026-11-27T08:20:55Z', '--follow-traces')
python -m opspilot diagnose-auto @range --plan "调查 gateway 故障"
python -m opspilot diagnose-auto @range "调查 gateway 故障"
python -m opspilot report TASK_ID
python -m opspilot report TASK_ID --format markdown
```

预览会列出服务、时间窗、候选触发条件、只读 GET 次数和查询预算。执行只从所选服务、所选时间窗两端（含边界）以内的 `ERROR`、`CRITICAL` 和 `FATAL` 日志获取候选。16 或 32 位非零十六进制 ID 统一转为 32 位小写，同一请求取时间最新的一行，时间相同取文件中先出现的一行。超过 3 个时优先查询最近出错的 3 个不同请求。报告保留候选的日志行号、时间和级别，以及缺失、无效、重复和超出查询上限的计数。

所有追踪查询共用 10 秒预算，单次查询也受 `jaeger.timeout_seconds` 约束。达到预算后，尚未开始的候选显示跳过原因。已保存报告可按任务 ID 回读，其中 `Request trace follow-ups` 将候选关联到同一份报告的跨度、查询结果和缺口。`linked` 表示返回跨度能够相连，`not_found` 表示后端无匹配，`unavailable` 表示查询或解析无法建立可归属的证据，`incomplete` 表示已有跨度但仍有缺口。服务窗口结论和请求跨度有各自的证据范围。采样和保留策略决定 Jaeger 可返回的跨度，观察到的错误仍需进一步确认业务原因。

## 隔离验收

使用 Jaeger 2.23.0，示例的 gateway 与 orders 通过本机 HTTP 传递 `traceparent`，由示例程序写入隔离 Jaeger。脚本将真实故障响应的 Trace ID 写入历史日志夹具，同时加入重复、相邻服务、窗外错误、非错误和一个在 Jaeger 中不存在的 ID。健康与 Prometheus 查询使用本机固定夹具响应，追踪读取转发给真实 Jaeger，脚本逐项记录查询方法、路径与响应码。

```powershell
docker run --detach --rm --name opspilot-incident-trace-example -p 127.0.0.1:16686:16686 -p 127.0.0.1:4318:4318 cr.jaegertracing.io/jaegertracing/jaeger:2.23.0
python examples/jaeger-request-trace/incident_followup_acceptance.py --query-url http://127.0.0.1:16686 --otlp-url http://127.0.0.1:4318 --output .opspilot/incident-trace-example
docker stop opspilot-incident-trace-example
```

每次使用新的输出目录。脚本保存配置、日志、计划、SQLite、JSON／Markdown 报告、Jaeger 原始响应、`observed-jaeger-gets.json` 和 `verification.json`。复跑会生成新的请求 ID 和任务 ID。

2026-11-27 验收任务 `1640a49b-62df-40af-8821-30b024d1550a` 的实际 HTTP 响应为 gateway `502`、orders `503`。预览未读 Jaeger，执行时只发出以下两次 GET。按任务 ID 从 SQLite 回读，JSON 与诊断时的结果相同，Markdown 同时列出两个候选，报告跨度与 Jaeger 原始记录逐字段一致。
