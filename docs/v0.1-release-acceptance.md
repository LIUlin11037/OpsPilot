# OpsPilot v0.1 发布前验收

2026 年 11 月 23 日，以 `f14c614` 为基线，在 Windows 上用 Python 3.10.11 和 Docker Desktop 复验。OpsPilot 通过只读接口采集证据。测试消息、服务启停和数据库初始化均发生在本轮新建的隔离实例。

| 验收项 | 实际观测 |
| --- | --- |
| RabbitMQ 3.13.7 | Python 和 Java 目标各通过 2 条用例。覆盖待投递、已投递待确认、队列清空、消费者持续返回 503 和恢复到 204。队列清空后的默认检查保留了跳过的端点及条件，复查对比也显示了这一条件。 |
| NGINX、Go、MariaDB 示例 | 健康基准为 HTTP 200、MariaDB 查询成功。停止独立 MariaDB 后，HTTP 返回 500，数据库错误码为 2003，诊断为 `undetermined`。恢复数据库后，默认复查在 HTTP 200 时记录依赖跳过，显式复查确认数据库健康。两种复查均与故障报告做了对比。 |
| Docker Example Voting App | 1 条真实验收用例通过。验证投票排队、Worker 恢复后入库，以及 Redis 不可用时仍保留 PostgreSQL 证据。 |

独立 Go 示例使用上游版本 `503c0dcef31b07fb77b2d4c5556bfafdf86f4f1a`，投票示例使用 `63e9150ca17af4ed05880d4245e486481f73fcb4`。 [独立示例复现说明](independent-service-acceptance.md)

## HireHub 投递通知

在独立 Docker 网络运行 HireHub `15ee3f9` 工作区中已有的 Delivery、Job 和 Notification JAR，使用 MySQL 8.0.46、RabbitMQ 3.13.7 和 Redis。Elasticsearch 替身只响应职位索引的启动检查。合成的投递与 Outbox 记录由实际 Java 服务发送和消费。OpsPilot 用专用 MySQL 查询账号和 RabbitMQ Management 监控账号读取证据。

| 验收场景 | 实际观测 | 通知分支 |
| --- | --- | --- |
| Notification 暂停 | Outbox 为 `CONFIRMED`，Job 已处理，通知查询成功且零行，通知队列待投递 1 条。 | `not_observed` |
| 查询账号缺少通知日志表读取权限 | MySQL 返回 `1142`，Job、Outbox 和队列证据仍可用。 | `unknown` |
| Notification 恢复 | 查到 1 条通知消费记录和 1 条收件人记录，待投递数归零。 | `observed` |

三轮均通过实时诊断、按任务 ID 回读报告和快照采集。隔离数据库中的投递状态在只读检查前后均为 `PENDING`，Job 投递计数为 1。验收后核对了三个 JAR 的 SHA-256，HireHub 已跟踪的源码文件与基线一致。 [HireHub 复现说明](hirehub-readonly-acceptance.md#重跑直连验收)
