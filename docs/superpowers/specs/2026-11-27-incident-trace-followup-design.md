# OpsPilot v1.7 从故障时段关联到具体请求

## 使用方式

用户给出目标配置和历史故障窗口。加上 `--follow-traces` 后，OpsPilot 从该目标已有的 JSONL 错误日志提取 Trace ID，并复用 v1.6 的 Jaeger 读取。在原有历史故障报告中显示服务层观测和单次请求的证据。基线为本地 v1.6 `44d1650`。[故障时段调查](../../v1.2-incident-window.md) · [按 Trace ID 追踪请求](../../v1.6-request-trace.md)

```powershell
python -m opspilot diagnose-auto --config target.json --incident-start $start --incident-end $end --follow-traces --plan "检查这段故障"
python -m opspilot diagnose-auto --config target.json --incident-start $start --incident-end $end --follow-traces "检查这段故障"
python -m opspilot report TASK_ID --format markdown
```

## 候选选择

| 方案 | 取舍 |
| --- | --- |
| 最近出错的请求，已选 | 优先核对窗口里最新的错误。一个请求只占一个名额。 |
| 最早出错的请求 | 从窗口起点复查。窗口内情况变化较多时，较晚的错误可能没有进入有限查询范围。 |

- 在现有 JSONL `timestamp`、`service` 和 `level` 之外，识别可选字段 `trace_id`。只有匹配配置的服务名、落入包含端点的窗口，且级别为 `ERROR`、`CRITICAL` 或 `FATAL` 的记录参与。使用 v1.6 的精确 ID 规范化。缺失或无效字段仍按原规则计入错误日志，并分别记录数量。
- 将同一规范化 ID 的重复错误合并。保留最新一条作为依据。时间相同时选文件中较早的行，候选之间也按同一规则排序。保存最多 3 个不同候选和各自的一基行号、时间、级别。报告列出缺 ID、无效 ID、重复和超过数量上限的计数，日志正文留在来源文件中。
- `--follow-traces` 仅在历史窗口模式下使用，需要现有 `jaeger` 配置。计划预览说明目标服务、窗口、日志来源、条件触发、最多 3 次精确 GET 和追踪阶段合计 10 秒的预算。预览阶段只解析配置。

## 执行与报告

- 先保留原有 HTTP、日志和指标观测。Core 根据有依据的候选决定是否追加读取，只使用配置的 Jaeger 端点。每个请求使用连接器超时时间和阶段剩余预算中的较小值。预算耗尽后，后续候选标记为未查。
- 每条请求摘要引用原日志证据索引和代表行。将 v1.6 的查询及跨度证据加入同一份报告，保证引用指向新的全局索引。链路完整性、下游错误和上游可能传播沿用 v1.6 的判断。服务层结论保持基于原有窗口证据，请求相关性以准确匹配的日志和跨度为依据。
- 无候选、日志不可用、超时、访问被拒、无匹配、缺失跨度或预算用尽时记录各自的缺口。已取得的日志、指标和跨度仍可按任务 ID 回读。旧日志、旧配置和未启用追踪的报告沿用原有结构。

## 验收与提交

- 默认测试固定时间窗，覆盖相邻服务、窗外日志、非错误级别、缺失或非法 ID、大小写和重复 ID、同秒排序、超过三个候选、预算用尽及查询失败。复验独立 `--trace-id` 和 v1.5 离线用例。
- 复用 v1.6 两服务样例和隔离 Jaeger，同一历史窗口内放入实际下游故障的请求记录、没有跨度可读的候选、重复日志、邻居和窗外错误。校对实际查询和报告引用，保存任务 ID、复现命令与覆盖边界。OpsPilot 侧使用只读接口，HireHub 源码保持原样。
- 用可单独验证、回退的小提交交付。提交前运行 `python -m opspilot` 和 `python -m pytest`。推送、合并、标签和发布另行授权。
