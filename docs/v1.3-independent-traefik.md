# v1.3 Traefik 独立接入验收

本轮预留此前未用于 OpsPilot 开发或接入的 Traefik。隔离环境运行 Traefik 3.8.0、两个 NGINX 后端及 Prometheus 3.13.5。两个路由都走真实反向代理，只有 `orders` 后端在验收中短暂停止。[Traefik 服务指标](https://doc.traefik.io/traefik/reference/install-configuration/observability/metrics/) · [访问日志字段](https://doc.traefik.io/traefik/reference/install-configuration/observability/logs-and-accesslogs/#json-format-fields)

| 入口 | 范围 |
| --- | --- |
| `http://127.0.0.1:18771/orders/` | 目标的当前 HTTP 状态 |
| `http://127.0.0.1:18771/neighbor/` | 同一代理上的相邻路由，用于原始观测对照 |
| `http://127.0.0.1:18772` | Prometheus，只读范围查询。抓取阶段保留 `orders@file` 并将响应码标签从 `code` 映射到 `status` |
| 专用日志副本 | 从隔离 Traefik 导出的访问日志。转换程序保留两条路由的服务标识、请求开始时间和出站响应码，5xx 映射为 ERROR |

预期健康时两个路由返回 200。停止 `orders` 后，目标路由返回 502 或 504，相邻路由仍返回 200。HTTP 报告可确认当次目标响应，指标可回答目标服务一段时间内的请求失败占比和 p95 延迟。历史报告应记录已过去的异常窗口及当前端点的状态。业务请求归因使用专属的准确标识，本示例的证据范围是路由和服务。

## 环境准备

在仓库根目录启动专用实例。首次验收使用已安装的 `1.3.0rc1`，当前复现使用 `1.3.0rc2`。使用已有 wheel 时，可以用 Python 3.10 构建虚拟环境并离线安装。准备时间单独记录。[独立验收结果和候选包](v1.3-acceptance.md)

```powershell
docker compose -p opspilot-v13-traefik -f examples/traefik-acceptance/compose.yaml up -d --wait
curl.exe -sS -o NUL -w "%{http_code}\n" http://127.0.0.1:18771/orders/
curl.exe -sS -o NUL -w "%{http_code}\n" http://127.0.0.1:18771/neighbor/
curl.exe -sS -o NUL -w "%{http_code}\n" http://127.0.0.1:18772/-/ready
```

2026 年 11 月 26 日准备环境时，原始请求观测到两个路由均为 200。在专用后端停机演练中，目标路由返回 504，相邻路由保持 200，Prometheus 和访问日志均存在目标的 5xx 观测。交付前恢复两条路由的 200。候选包通过独立虚拟环境离线安装、依赖核对和模块启动，wheel 的 SHA-256 为 `8a9c32bfd7871ed502065a63d78cde590f2012be0053a2330ffee3973b76b3b4`。

需要重新准备候选环境时，从同一验收基线构建 wheel 和依赖轮子。安装使用本地 wheel 目录。

```powershell
$candidate = ".opspilot/v13-rc2"
python -m pip wheel --wheel-dir "$candidate/wheelhouse" .
python -m venv "$candidate/install-env"
$python = "$candidate/install-env/Scripts/python.exe"
& $python -m pip install --no-index --find-links "$candidate/wheelhouse" "opspilot==1.3.0rc2"
& $python -m pip check
& $python -m opspilot
```

## 首次使用者的任务

1. 从环境就绪开始计时，阅读目标配置指南，在独立工作目录保存三个配置和 SQLite。先建立 **HTTP 配置**，服务 URL 使用 `/orders/` 的完整地址。再复制成 **指标配置**，加入 Prometheus 地址，`service` 设为 `orders`，窗口 30 秒、步长 5 秒。错误率使用 `traefik_service_requests_total`、`ratio`、阈值 0.1。p95 延迟使用 `traefik_service_request_duration_seconds_bucket`、`seconds`、阈值 0.2。历史配置在整理日志后从指标配置添加日志路径。[HTTP 接入](first-http-target.md) · [指标字段示例](../examples/prometheus-health/target.json)
2. 用计划预览确认来源。按下方命令生成正常流量，运行指标配置的 `diagnose-auto --check-metrics`。按任务 ID 从 SQLite 回读首份 Markdown 后停止计时。首份报告以 30 分钟内为目标，计入阅读、配置、预览和暖流量。保留任务 ID、实际用时、改动和卡点。
3. 停止专用 `orders` 服务，生成 90 秒流量并保存输出。保持故障状态，先用 HTTP 配置诊断，再用指标配置诊断。每次从执行诊断到按 ID 回读计时，记录各自的 `tool_calls` 和额外指标查询数。直接按指标报告的表达式、起止时间和步长向 Prometheus 查询，保存原始响应。比较两个报告中能由证据支持的具体判断。
4. 恢复 `orders`，等两个路由都返回 200。用正常流量填满指标窗口后运行恢复复查。将访问日志导出到工作目录，给历史配置加上 `health.service_log_path`，用故障流量输出的整秒起止时间生成历史调查报告。检查当前 HTTP 状态、历史指标、日志数量和证据索引。记录相邻流量是否计入目标范围。[历史时段调查](v1.2-incident-window.md)

### 流量与日志命令

```powershell
$python = ".\.opspilot\v13-rc2\install-env\Scripts\python.exe"
$compose = @("compose", "-p", "opspilot-v13-traefik", "-f", "examples/traefik-acceptance/compose.yaml")
& $python examples/traefik-acceptance/workload.py --seconds 90
docker @compose stop orders
# 故障流量与两份诊断均在专用 orders 停止期间完成
& $python examples/traefik-acceptance/workload.py --seconds 90
docker @compose start orders

# $work 指向本次验收的工作目录
docker @compose logs --no-log-prefix --no-color traefik | Set-Content -Encoding utf8 (Join-Path $work "access-raw.jsonl")
Get-Content (Join-Path $work "access-raw.jsonl") | & $python examples/traefik-acceptance/capture_logs.py | Set-Content -Encoding utf8 (Join-Path $work "service.jsonl")
```

发生故障或中断时，恢复步骤使用同一 Compose 项目的 `start orders`，随后核对两个路由。报告证据中的 `expression`、`window_start`、`window_end` 和 `step_seconds` 对应 Prometheus 的 `query`、`start`、`end` 和 `step` 参数。历史报告查询从 `evaluation_start` 开始复核。原始查询与诊断耗时分开记录。[Prometheus 范围查询 API](https://prometheus.io/docs/prometheus/latest/querying/api/#range-queries)

交回三份配置、首次和故障对照的用时、各阶段任务 ID、SQLite、原始指标、原始与转换后的日志，以及一项由指标支持的新判断。用独立记录列出执行中遇到的问题和为接入改动的文件。
