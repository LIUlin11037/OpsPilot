# OpsPilot v0.4 多步调查

在同一个 `target.json` 为相关服务和队列配置 `health.service_url`、`rabbitmq.management_url` 和 `rabbitmq.queue`。关联由接入者明确配置。可选的 `rabbitmq.consumer_health_url`、`rabbitmq.processing_url` 或 `rabbitmq.processing_record` 扩充调查范围。RabbitMQ 只读凭据通过现有环境变量提供。

在仓库根目录运行下列命令，替换配置文件和消息 ID。去掉 `--message-id` 时只做服务和队列范围的检查。

```powershell
$python = ".\.venv\Scripts\python.exe"
$investigation = @("diagnose-auto", "--config", "target.json", "--workflow", "investigation", "--message-id", "order-101", "订单为什么延迟？")
& $python -m opspilot @investigation --plan
$run = & $python -m opspilot @investigation | ConvertFrom-Json
& $python -m opspilot report $run.task_id --format markdown
```

计划列出每种可能的读取、条件、来源和预算。预览只解析配置，无需 RabbitMQ 凭据，报告库在执行时创建。

| 读取 | 触发条件 |
| --- | --- |
| HTTP 服务 | 调查起点。端点报告健康时结束本次调查。 |
| RabbitMQ 队列 | HTTP 服务异常，或无法确认健康。 |
| 消费者健康 | 配置了消费者端点，且队列有待投递或待确认消息，或队列来源不可读。 |
| 消息处理记录 | 服务异常或未知，且传入明确的消息 ID 和已配置的处理记录来源。队列状态用于描述队列，处理记录按队列、虚拟主机和精确消息 ID 读取。 |

报告的 `investigation.decisions` 记录每次动作的触发依据，以及本次 `evidence` 中从 0 开始的引用索引。若注册消费者数量与消费者健康端点给出不同信号，两项证据均保留，并列出它们的索引。两种观测来自独立读取，报告将根因保留为 `undetermined`。

默认预算为 4 次读取和 15 秒，可用 `--max-steps` 和 `--max-seconds` 调整。流程在预算耗尽后停止发起新读取，每次网络读取的套接字超时取来源配置和剩余时间的较小值。已经开始的读取依赖连接器返回，DNS、分段响应或本地文件读取可能使报告中的总耗时超过预算。停止原因记录在 `investigation.stop_reason`，已获得的证据仍可回读。

## 隔离演示

演示在本机随机端口模拟服务、RabbitMQ Management API、消费者和处理记录端点。它用同一问题完成五个场景，保存计划、SQLite、原始 JSON 和回读的 Markdown。

```powershell
.\.venv\Scripts\python.exe examples/auto_diagnosis_demo.py --investigation
```

| 场景 | 验收现象 |
| --- | --- |
| 服务健康 | 只查 HTTP，记录 `service_healthy`。 |
| 服务异常 | 检查队列、消费者和指定消息。注册消费者与端点健康不同，处理结果仍归属指定消息。 |
| 队列超时 | 保存服务和队列超时证据，按配置继续查消费者和精确消息。 |
| 步数耗尽 | 只完成第一项读取，记录 `step_budget_exhausted`。 |
| 时间耗尽 | 记录 `time_budget_exhausted` 并保留之前的观测。 |
