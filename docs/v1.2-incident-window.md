# 按故障时段调查

用 `diagnose-auto` 指定事件的起止时间，在一份报告中查看当前 HTTP 端点和同一服务过去的日志及指标。两次诊断可以使用相同的历史窗口，跟踪当前端点是否恢复。

## 配置与用法

在包含 `health` 与 `prometheus` 的目标配置中设置 `health.service_log_path`。相对路径以目标配置文件所在的目录为准。JSONL 中的 `service` 与配置的 `prometheus.service` 和抓取任务的 `job` 精确匹配。服务无归属的窗口内日志计入覆盖缺口，能归属到相邻服务的日志各自留在原范围。[Prometheus 目标配置](v1.1-prometheus.md#配置)

```jsonl
{"timestamp":"2026-11-26T10:30:12+08:00","service":"orders","level":"ERROR"}
```

按实际故障填写起止时间。时间格式使用带时区的 ISO 8601，精确到整秒。窗口为 65 至 900 秒，结束时间须已到达。

```powershell
$start = "2026-11-26T10:30:00+08:00"
$end = "2026-11-26T10:31:20+08:00"
python -m opspilot diagnose-auto --config target.json --incident-start $start --incident-end $end --plan "排查这一段故障"
python -m opspilot diagnose-auto --config target.json --incident-start $start --incident-end $end "排查这一段故障"
python -m opspilot report TASK_ID --format markdown
python -m opspilot compare-http ONGOING_ID RECOVERED_ID --include-service-log --format markdown
```

预览列出当前 HTTP 探针、本地 JSONL 和 Prometheus 查询。Prometheus 的首个求值点是窗口开始后 60 秒，保证一分钟滚动查询只取窗口内的原始样本。日志按窗口起止时间取证。固定窗口与当前 HTTP 观测时间分别保存在报告中。[Prometheus 范围向量选择器](https://prometheus.io/docs/prometheus/latest/querying/basics/#range-vector-selectors)

JSON 与 Markdown 通过从 0 开始的索引引用当前端点、历史观测、异常依据和覆盖缺口。可读来源中的异常在其他来源缺失时仍保留。只有全部可用窗口证据都未观察到异常且范围完整时，历史状态才是 `no_anomaly_observed`。单条请求归因需要能匹配该请求的业务标识。

## 隔离复验

复用 v1.1 的轻量服务和 Prometheus。示例在持续产生 HTTP 503 时生成第一份报告，恢复端点后对同一历史窗口生成第二份报告，最后使用指向缺失日志的配置生成第三份报告。脚本在日志副本里加入相邻服务及窗口外的错误，用原始服务日志与 Prometheus 响应核对结果。

```powershell
docker compose -p opspilot-v11-prometheus -f examples/prometheus-health/compose.yaml up -d --wait
python examples/prometheus-health/incident_acceptance.py .opspilot/v12-incident-acceptance
docker compose -p opspilot-v11-prometheus -f examples/prometheus-health/compose.yaml down --volumes
```

## 实测记录

2026 年 11 月 26 日，用 Prometheus 3.13.5 及其隔离的 `orders` 目标复验。三次诊断使用同一窗口，即北京时间 11:02:35 至 11:03:55。原始服务日志有 148 条属于该窗口的目标错误，额外加入的一条相邻服务错误及两条窗口外错误均未计入。两项指标的峰值均与按报告记录的表达式和求值范围查询到的原始结果一致。

| 阶段 | 回读任务 ID | 当前 HTTP | 历史异常证据索引 | 停止原因 |
| --- | --- | ---: | --- | --- |
| 故障时调查 | `43e8316b-667f-4759-8fbd-44a26388cce9` | 503 | `1, 2, 3` | `checks_complete` |
| 恢复后调查同一窗口 | `6d1b0130-cdda-4386-bcf9-26d81cd3d67e` | 200 | `1, 2, 3` | `checks_complete` |
| 日志源缺失 | `4c84d26b-0539-4168-97b1-1d0a5723d631` | 200 | `2, 3` | `sources_incomplete` |

这三份报告的索引 0 是当前 HTTP，1 是日志，2 和 3 是同一服务的历史指标。第三次运行把日志索引 1 标为 `log_not_found`，两项指标仍标明历史异常。前两份报告的对比记录 HTTP 503 到 200，历史日志没有变化，两项指标均可配对。三个任务的 SQLite、JSON、Markdown、原始指标响应及对比存于本地 `.opspilot/v12-incident-final/`。

从旧 SQLite 回读了 v1.0 的 `6deeb50d-734a-43a8-b8c9-1e6248a57a1f` 和 v1.1 的 `19149a09-b552-40f1-b5a6-07980e28b951`。JSON、Markdown 和数据库摘要均与原记录一致。
