# OpsPilot 从 v0.1 到 v1.0 的实施方案

基线日期为 2026 年 11 月 23 日。**v1.0 的交付目标是让一位没有参与 OpsPilot 开发的工程师，把一个新的微服务项目接进来，独立完成一次有证据、可复查的故障诊断。** 接入者提供已获授权的只读入口。通用故障通过配置接入，业务问题通过带有关联标识的业务检查点接入。下文版本号与验收门槛均为规划值，进度以实际验收记录为准。

## 用户最终能做什么

以“订单已受理，但通知迟迟没到”为例。工程师选定目标，输入问题和订单标识。OpsPilot 展示可以检查的范围，核对已配置的服务、队列和业务记录，再依据每一步观测决定是否继续。队列积压能说明系统有待处理的消息；要判断这张订单停在哪一步，还需要能与该订单关联的处理记录。

理想的报告能回答四个问题：最后确认成功的是哪一步，异常或证据缺口最早出现在哪里，哪些观测支持这一判断，接下来查什么最能缩小范围。如果通知记录读取被拒绝，报告保留之前的成功观测，标出缺少哪项读取权限。运维人员在外部恢复服务后，可以复查同一订单，看见新增的处理记录，以及哪些先前异常仍待验证。

| 接入条件 | 应能回答的问题 | 达标边界 |
| --- | --- | --- |
| 只提供已支持的健康端点、队列或依赖读接口 | 哪个已配置来源有异常，哪些检查成功、失败或按条件跳过？ | 新项目仅提供配置和凭据引用，检查范围可预览。 |
| 另提供请求、消息或业务 ID 及可查询的检查点 | 这一次请求走到了哪一步，哪个分支还缺证据？ | 领域映射放在目标适配器。相邻时间或全队列积压本身不足以证明单条请求失败。 |
| 项目使用尚未支持的组件，或缺少观测权限 | 当前还能确认什么，要补哪个入口或权限？ | 报告明示覆盖缺口。新协议由连接器扩展，经真实验收后列入支持范围。 |

## 起点与差距

v0.1 已有手动提交任务、按症状词和显式参数路由、流程内按证据追加检查、只读业务追踪，以及 SQLite 报告回看和前后对比。发布前默认测试 330 项通过、5 项按配置跳过。另行完成了真实 RabbitMQ、NGINX/Go/MariaDB、Docker Example Voting App 和 HireHub 隔离场景验收。HireHub 使用已有 Java 服务及启动所需的 Elasticsearch 替身。[v0.1 验收记录](v0.1-release-acceptance.md)

已有验收说明同一工具能用于不同技术栈。接下来的工作要验证四个更高要求：陌生人能独立接入，Core 能跨项目追踪新的业务链路，调查能在多个相关来源之间有界地继续，执行中断后仍能恢复并解释已有观测。已完成的发布前验收与正式发布分别记录。

## 实施顺序与完成条件

| 阶段 | 交付目标与主要工作 | 通过什么判断完成 |
| --- | --- | --- |
| v0.2 通用接入 | 复用现有目标 JSON、计划预览和 HTTP 流程，交付最小配置样例、可读的配置错误及首次接入指南。整理组件覆盖表，逐项区分健康检查、业务追踪、快照和实时读取。 | 由新对话 Codex 仅用文档、配置和只读入口接入此前未用于开发的项目，完成健康基准、故障、恢复和报告对比。计时从项目和只读访问就绪后开始，到读出首份报告结束，目标为 30 分钟内。保留配置、耗时和所遇障碍。 |
| v0.3 业务链路可迁移 | 对照 HireHub 与 Voting 的现有适配器，提炼关联标识、检查点、证据来源及状态的最小契约。在另一个业务领域实现一条链路，复用通用追踪和报告。 | 新适配器用相同任务入口区分“查到记录”“查询成功且零条”“无法读取”。混入另一个 ID 的记录后仍能正确归属。新增目标专属代码限于适配器与入口注册，Core 无需添加该项目的分支。 |
| v0.4 多步调查 | 在现有 LangGraph 流程上实现一个跨来源场景，如 HTTP 端点异常后检查关联队列、消费者及该消息的处理记录。为每个后续动作记录触发依据，设定步数与耗时上限，并记录停止原因。 | 用同一故障描述、不同观测驱动至少两条不同工具路径。正常、部分来源超时、证据矛盾、预算用尽均能生成报告。未配置的来源不会被访问，每个判断能追溯到本次观测。 |
| v0.5 可靠执行 | 在第一次外部读取前分配任务 ID，持久化已完成步骤和任务状态。定义中断恢复、有限重试、重复恢复请求以及观测过期后的复查语义。 | 在一次成功读取后中断进程，重启后能按原 ID 查看并继续。两个恢复请求不会重复记入同一步结果。重新采集保留新旧观察时间；v0.1 保存的报告仍能回读。 |
| v0.6 可选模型辅助 | 在规则流程旁试验自然语言理解和下一步工具建议。模型只可建议已注册工具及结构化参数，调用前由程序校验范围和预算。密钥从环境读取，记录发送给模型的数据范围。 | 在同一批事先标注的改写、歧义和证据不足案例上，对照规则路径记录正确选路数、误判、调用成本和耗时。只有带来额外正确选路且未增加错误归因时才启用该能力。缺密钥、模型超时或建议越界时，离线基础诊断仍可完成。模型收益不达标时，可按规则路径进入 v1.0 验收。 |
| v1.0 独立验收与发布 | 冻结支持矩阵、配置和报告兼容范围。在干净环境完成安装、第三方接入、故障调查、中断恢复和交接，交付版本说明、复现材料与已知限制。 | 通过下节全部验收。公布测试所用版本、报告和缺口，将发布标签关联到同一次通过验收的提交。 |

## v0.2 的交付任务

1. **让第一次配置可以照着做。** 从现有 README 和 Go 示例提取一份最小 HTTP 目标配置及接入说明，列明要替换的地址、只读权限和报告位置。用现有 `diagnose-auto --plan` 预览，随后执行诊断并按任务 ID 回读。先验证这条路径，再决定需要改哪一条提示。[现有 CLI 用法](../README.md#按故障描述选择诊断流程)
2. **让接入失败也能指出下一步。** 用本地样例分别制造配置字段写错、端点无法连接、已配置依赖读取失败。验证配置错误能定位字段、执行错误能定位来源、已有证据仍可回读。仅修复实际发现的缺口，并为每个修复保留回归用例。
3. **由新对话 Codex 完成一次新项目接入。** 选择一个可本机隔离运行、带现成健康端点和可停用依赖的非 HireHub 项目，固定上游版本。按指南独立运行，记录首次出报告耗时，再完成故障与恢复对比。[Gitea 独立接入记录](v0.2-onboarding-acceptance.md)

## v1.0 的最终验收

- **陌生项目。** 保留一个未参与前述开发和调参的项目做最终验收。交给首次使用者配置，达到 v0.2 的首份报告时间目标。检查接入改动清单，通用诊断只需目标配置；如需业务归因，单独记录适配器工作量。
- **有根据的结论。** 预先写下每个案例可被证据支持的最深结论及应有的未知项。至少覆盖健康基准、HTTP 依赖故障、队列积压、单条业务记录缺失、权限不足、来源超时或矛盾、恢复复查。逐例核对定位、证据和停止原因。任何把“无法读取”判为“业务失败”、串用其他 ID、或把跳过的来源判为健康的情况均阻止发布。
- **执行与兼容。** 在隔离环境重现中断和重复恢复，核对任务 ID、步骤、观测时间和最终报告。回读旧版真实报告，在 JSON 与 Markdown 中核对关键结论。用两次实际诊断演示故障到恢复的差异。
- **真实环境回归。** 复跑 RabbitMQ、独立项目和 HireHub 已覆盖的只读场景，分别记录离线与真实验收结果。应用启动和默认测试须在没有模型密钥时通过。对外发布材料列出已验证的组件、版本、观测深度及限制。[HireHub 验收范围](hirehub-readonly-acceptance.md)

## 开发与范围控制

每个任务围绕一条可从 CLI 观察的行为展开，用轻量模拟验证分支，在阶段结束时用隔离真实服务复验。提交前运行 `python -m opspilot` 和 `python -m pytest`。在阶段验收记录中写下输入、预期、实际报告、未覆盖项和对应提交，供下一位接手的人复跑。

Core 负责选工具和解释证据，Connector 负责读取基础设施，Adapter 负责目标的领域映射。若新项目必须修改 Core 才能读取专属业务字段，先用已有目标复核契约。OpsPilot 的执行权限保持只读，故障注入和恢复由隔离验收环境承担，HireHub 源码保持原样。自动告警、自动修复、复杂前端和大型监控平台留待 v1.0 之后单独立项。[项目开发约定](../AGENTS.md)
