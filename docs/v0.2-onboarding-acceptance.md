# OpsPilot v0.2 通用接入验收

验收目标为此前未用于 OpsPilot 开发的 Gitea 1.25.1 和 PostgreSQL 16.11。使用固定版本的上游镜像，Compose 创建独立网络和数据卷。Gitea 的端口仅绑定本机，PostgreSQL 没有对主机发布端口。OpsPilot 只需要 Gitea 的只读健康地址，不需要登录、数据库凭据或项目适配器。[Gitea Docker 部署文档](https://docs.gitea.com/1.25/installation/install-with-docker/)

## 准备环境

在仓库根目录启动本次验收环境。如果容器已经运行，`up -d` 会复用已有实例。

```powershell
docker compose -p opspilot-v02-gitea -f examples/gitea-health/compose.yaml up -d
curl.exe --max-time 5 -i http://127.0.0.1:18742/api/healthz
```

等到健康端点返回 HTTP 200，并且响应中的 `checks` 包含 `database:ping` 为 `pass`。服务首次启动会初始化数据库，可能需要稍候。启动所需的镜像下载、Python 环境安装及就绪等待均在计时之前完成。

## 独立验收

v0.2 由未参与编写指南的新对话 Codex 独立执行。环境和只读地址就绪后，在 PowerShell 运行 `$started = Get-Date`，再按指南完成配置、预览、诊断和回读。主服务地址为 `http://127.0.0.1:18742/api/healthz`。读到保存的 Markdown 报告后运行 `(Get-Date) - $started`，记录耗时，目标为 30 分钟内。[首次接入 HTTP 目标](first-http-target.md)

读到健康基准后，按下列步骤制造故障并复查。停启操作只用于本页的隔离 Compose 项目，由验收人员执行。

1. 执行下列命令停止数据库。使用 `curl.exe --max-time 5 -i http://127.0.0.1:18742/api/healthz` 核对 HTTP 424，然后生成故障报告。

   ```powershell
   docker compose -p opspilot-v02-gitea -f examples/gitea-health/compose.yaml stop postgres
   ```

2. 启动数据库。等健康端点重新返回 200，生成恢复报告。用指南里的 `compare-http` 查看健康到故障、故障到恢复两次变化。

   ```powershell
   docker compose -p opspilot-v02-gitea -f examples/gitea-health/compose.yaml start postgres
   ```

3. 记录实际耗时、三份报告的任务 ID、两次对比的状态变化、需要修改的文件和遇到的障碍。通用接入应只改本地目标 JSON。独立结果需要由操作人确认。

如需释放容器和端口，结束后在仓库根目录运行以下命令。项目专用数据卷留作复跑。

```powershell
docker compose -p opspilot-v02-gitea -f examples/gitea-health/compose.yaml down
```

## 判定依据

| 场景 | Gitea 原始响应 | OpsPilot 保存的观测 |
| --- | --- | --- |
| 健康基准 | HTTP 200，数据库检查通过 | `observed`、`healthy`、`no_failure_observed` |
| 数据库停机 | HTTP 424，数据库检查失败 | `observed`、`unhealthy`、`undetermined` |
| 数据库恢复 | HTTP 200，数据库检查通过 | `observed`、`healthy`、`no_failure_observed` |

Gitea 返回体里的数据库检查由验收人员独立核对。OpsPilot 的通用 HTTP 路径采集状态码，报告停机阶段的端点异常和可采取的后续检查。 [Gitea 健康端点的实现](https://github.com/go-gitea/gitea/blob/v1.25.1/routers/web/healthcheck/check.go)

## 验收记录

### 开发方自测

2026 年 11 月 23 日在 Windows、Python 3.10.11、Docker 29.3.1 运行。环境就绪后，自动化复跑从复制和修改样例开始，经预览、执行和按 ID 回读 Markdown，耗时 7.64 秒。目标接入只改本地 JSON，将 `health.service_url` 换成隔离环境的 Gitea 地址。

`python -m opspilot` 启动成功。默认 `python -m pytest` 通过 334 项，按默认配置跳过 5 项。Gitea 真实轮测单独执行。

| 场景 | 本地任务 ID | 验证结果 |
| --- | --- | --- |
| 健康基准 | `b11babca-b1b1-4f2d-9ace-2ead1474564e` | 200，计划中的来源与回读报告一致。 |
| 数据库停机 | `5b4a75ce-fb83-4c4f-8102-35282ee40682` | 424，保存为已观测到的端点异常。 |
| 数据库恢复 | `e581cfde-ff97-4fdc-b1e1-e80d195d328f` | 200，复查恢复为无已观测故障。 |

三份报告从 SQLite 按任务 ID 回读，JSON 与初次输出一致。两次对比的 JSON 和 Markdown 均核对了端点和状态变化 200 → 424 → 200。原始响应另外核对了 Gitea 的 `database:ping` 结果。配置拼写错误会列出 `servce_url` 并返回退出码 2。连不上的主端点会保存 `unknown / transport_error`。显式检查两个依赖时，第一个无法连接，回读报告仍保留主端点的 200、失败依赖的地址及原因，以及后续依赖的 200。

首次试跑发现 Gitea 官方镜像仓库连接中断，换用同版本 Docker Hub 发布镜像后启动成功。OpsPilot 原先把 424 归为无法判断端点健康，修复后作为已观测到的端点异常，同时保持整体原因为 `undetermined`。报告、对比和原始响应保存在本地 `.opspilot/v02-self/`。

本次验收使用的镜像摘要如下。

- `gitea/gitea@sha256:b3aee0f6fa4ff3271180a2388bb796be5cced8828685b968a310d70e881fcbb3`
- `postgres@sha256:4327b9fd295502f326f44153a1045a7170ddbfffed1c3829798328556cfd09e2`

### 新对话模型独立验收

2026 年 11 月 23 日，由新对话中的 Codex 按本页和首次接入指南执行。环境就绪后，从开始配置到按任务 ID 读出首份已保存的 Markdown 报告，用时 **4.81 秒**，达到 30 分钟内的目标。接入只修改了本地 JSON 的 `health.service_url`。

| 场景 | 任务 ID | Gitea 原始响应 | OpsPilot 诊断状态 |
| --- | --- | --- | --- |
| 健康基准 | `c21196db-e602-4412-b4ad-d59d2e580008` | 200，`database:ping` 通过 | `no_failure_observed` |
| 数据库停机 | `2d29bb75-53c2-4b2d-882a-11831955423c` | 424，`database:ping` 失败 | `undetermined` |
| 恢复复查 | `ae9001cc-c561-41ce-819f-08ba5e31ea6a` | 200，`database:ping` 通过 | `no_failure_observed` |

复核时从 SQLite 回读了三份报告，核对了配置、计划、计时和原始 HTTP 响应。重新生成的两份对比与保存的 Markdown 一致，显示 `200 / healthy → 424 / unhealthy → 200 / healthy`。模型执行日志记录的唯一卡点是默认权限无法访问 Docker。取得限定命令权限后，停启仅作用于本页指定的 PostgreSQL，验收环境恢复健康。该次运行记录了应用启动成功及默认测试 334 项通过、5 项跳过。原始材料位于本地 `.opspilot/first-http-model/`。

2026 年 11 月 23 日，项目确认以本次模型独立验收作为 v0.2 的结项依据，本阶段通过验收。
